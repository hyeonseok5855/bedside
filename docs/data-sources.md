# Data Sources

수집 레이어는 상시 백그라운드로 돌며 하루치 이벤트를 로컬 DB에 적립한다.
**"읽는" 것이 아니라 "쌓는" 것이다.** 이 앱은 AI 앱이라기보다 라이프로깅 앱 +
AI 인터뷰어이고, 공수의 상당 부분이 이쪽에 있다.

## v1 소스

| 소스 | 방법 | 난이도 | 비고 |
|---|---|---|---|
| 위치 / 출퇴근 | FusedLocationProvider + Geofencing. 집·회사 지오펜스 진입·이탈 로깅 | 중 | **구글 타임라인은 온디바이스로 옮겨져 API로 읽을 수 없다.** 직접 수집해야 한다 |
| 사진 | MediaStore로 당일 촬영분 조회 + EXIF(시각·GPS) | 쉬움 | v1은 메타데이터만. 내용 분석(vision)은 v2 |
| 몸무게 / 운동 / 수면 | **Health Connect** | 쉬움 | Google Fit API는 2026년 말 종료 예정이고 신규 가입도 막혔다. Health Connect가 유일한 경로 |

## 제외

**카카오톡 — 범위에서 완전히 제외.** 나중에 필요해지면 그때 다시 구상한다.

이유:

- 실질적으로 NotificationListenerService로 알림에 뜬 것만 읽을 수 있다.
  미리보기는 잘려 있고, 알림을 끄고 읽은 대화는 아예 잡히지 않는다
- DB 직접 접근은 루팅이 필요하다
- 상대방 발화가 그대로 외부 API로 나가는 구조가 된다

## 브리핑 방식

프로필과 하루 타임라인은 **tool로 lazy fetch하지 않고 프롬프트 앞단에
브리핑으로 프리로드한다.** 사용자가 "AI가 다 알고 구체적으로 물어봐도 된다"고
정했으므로 이 단순화가 가능하다. 왕복이 줄어 야간 대화의 지연도 줄어든다.

tool은 무겁거나 조건부인 것만 남긴다:

- 사진 상세 (v2, vision)
- 과거 일기 검색 (v2)

### 브리핑 사용 규칙

브리핑 내용을 나열하거나 확인받으면 안 된다. 프롬프트에 명시한다.

- 나쁨: "오늘 21시 40분에 퇴근하셨는데"
- 좋음: "오늘 퇴근이 늦었네요. 무슨 일 있었어요?"

## 저장 원칙

- **로컬 우선.** 원본은 기기 안에 있다. 서버는 API 호출 시에만 쓴다.
- **일기는 사용자 접근 가능 경로에 실제 마크다운 파일로 쓴다.**
  (`Documents/Diary/2026-07-27.md` 형태) 앱을 삭제해도 파일은 남는다.
- **사진은 복사하지 않고 MediaStore URI만 참조한다.** 갤러리에 그대로 남는다.
- **원시 타임라인 DB는 주기적으로 암호화된 단일 파일로 export**해서
  로컬 NAS나 Syncthing으로 흘린다. 서버에 "저장"하는 것이 아니라 백업 사본만
  둔다. (v2)
- **Android auto-backup은 믿지 않는다.** 조용히 실패한다.
- 대화한 날과 데이터만 있는 날을 DB에서 구분한다. "일기 없는 날 자동 요약"을
  붙일 때 필요하다.
