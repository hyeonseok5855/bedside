## 8. 프로필 레이어는 v1에서 자유 형식 마크다운으로만 간다

- 날짜: 2026-07-27
- 상태: 확정

장기 목표는 AI가 "나에 대한 전문가"가 되는 것이지만, 제대로 하면 그 자체로
프로젝트 하나다. 스키마를 설계하다가 일기 앱을 못 만들 수 있다.

`나에 대하여.md` + `인물/이름.md`를 직접 쓰고 통째로 프롬프트에 넣기만 해도
체감 효과의 8할이 나온다. 구조화·자동 갱신·노출 토글은 실제로 무엇이
필요한지 써보고 나서 붙인다.

### 관련 원칙 (v2 설계 시 유지)

- **AI가 프로필을 자동으로 쓰게 하지 않는다.** 대화에서 추론한 것을 AI가
  알아서 박아넣기 시작하면 그 추론이 다음 대화의 전제가 되고 편향이 눈덩이처럼
  굴러간다. 제안 → 사용자 승인 → 반영.
- **검사 결과는 참고용으로만.** AI가 그것으로 사람을 규정하기 시작하면
  질문의 질이 떨어진다. "이걸 근거로 사람을 규정하지 말 것"을 프롬프트에 명시.
- **코어 프로필(항상 주입)과 상세(tool 조회)를 이원화**한다. 인물이 30명이
  되면 이 구분 없이는 감당이 안 된다.

## 11. 앱 내부에서 MCP를 쓰지 않는다

- 날짜: 2026-07-27
- 상태: 확정

Anthropic API의 `mcp_servers` 파라미터는 URL 기반이라 온디바이스 데이터에는
무의미하다.

MCP는 위 10번처럼 **개발 단계에서만** 쓴다.

## 13. 일기는 대화 종료 즉시, 그날 밤에 생성한다

- 날짜: 2026-07-27
- 상태: 확정

세션이 종료되는 순간 그 자리에서 일기를 만든다. 다음 날 낮으로 미루지
않는다. 그날 결과를 그날 밤에 볼 수 있다는 즉시성이 이득이다.

따라오는 규칙:
- **무응답 타임아웃도 "종료"다.** 대화 중 잠들면 타임아웃으로 세션이 닫히고,
  그 시점에 일기 생성이 트리거된다. 즉 미완 대화도 밤에 생성 대상이 된다.
  (장면이 부실하면 짧은 일기가 나오는 것은 `diary-writer.md`의 "짧게
  이야기한 날은 짧게" 규칙으로 흡수된다.)
- 생성은 백그라운드 워커에 넘겨 UI를 막지 않는다. 밤의 생성 지연(수 초)은
  감수한다. 실패 시 재시도, 그래도 실패하면 transcript는 이미 커밋돼 있으므로
  다음 날 재생성할 수 있어야 한다.
- transcript는 항상 먼저 확정된다. 일기는 그 위의 파생물이다(`concept.md`).

## 14. 야간 대화 오디오 경로 — 스피커 + 반이중(끼어들기 없음)

- 날짜: 2026-07-27
- 상태: 확정

TTS 재생 중에는 마이크를 닫고, 재생이 끝난 뒤에 듣는다. 사용자가 TTS 도중
끼어드는(barge-in) 것은 v1에서 지원하지 않는다.

이유: 스피커로 재생하면서 마이크를 열면 TTS 소리가 되새어 들어와 STT가 자기
목소리를 받아 적는다. 이를 막으려면 음향 에코 제거(AEC)가 필요한데, 반이중으로
가면 그 문제 자체가 사라져 v1 공수가 크게 준다. 침대에서 스피커로 쓰는 맥락에도
자연스럽다.

트레이드오프: 사용자가 답하려면 AI 말이 끝나기를 기다려야 한다. 인터뷰어가
질문을 짧게(한 번에 하나) 던지는 규칙(`interviewer.md`)이 이를 완화한다.
barge-in과 전이중은 실사용에서 답답함이 확인되면 v2에서 AEC와 함께 재검토.

## 15. SQLCipher 키는 Keystore에 인증 없이 둔다

- 날짜: 2026-07-27
- 상태: 확정

DB 패스프레이즈를 Android Keystore에 저장하고, 세션 진입 시 별도 생체/잠금
인증을 요구하지 않는다.

막으려는 위협을 명시한다: **(a) 폰 분실·도난 시 저장소 덤프, (b) 앱 삭제 후
잔존 파일, (c) 백업 파일 유출.** "폰을 잠금 해제해 손에 쥔 사람"은 위협 모델에
넣지 않는다 — 개인 기기이고, 그걸 막으려면 매 밤 인증이 필요해 취침 전 UX와
정면충돌한다.

주의: 이 키는 기기에 묶인다. 따라서 v2의 "암호화 export → NAS" 백업은 **이
키와 별개의, 사용자가 정하는 키**로 잠가야 한다. 기기 Keystore 키로 백업을
잠그면 기기가 죽을 때 백업도 못 연다. 이 이원화를 export 스키마 설계 시점에
반영한다. (`open-questions.md` B6/B 잔여 항목 참고)

## 16. 이어하기 — 어제 미완 대화는 닫고 오늘은 새로 시작한다

- 날짜: 2026-07-27
- 상태: 확정

어제 세션이 미완인 채 오늘 밤이 되면, 어제 것은 어제로 닫고(있는 만큼 결정
13에 따라 일기화) 오늘은 오늘 데이터 브리핑으로 새 세션을 연다. 미완 대화가
날짜를 넘어 이어지지 않는다.

이유: 이어하기가 날짜를 넘나드는 순간 "하루 = 일기 한 편" 매핑이 깨지고,
어제·오늘 브리핑이 섞여 질문이 산만해진다. 빈 날이 흔하다는 사용 특성상
(`concept.md`) 며칠 전 대화를 억지로 잇는 것은 득보다 실이 크다.

`[heavy]`로 미뤄둔 무거운 주제는 이 결정과 무관하게 주간 회고에서 다시
꺼낸다(v2). "이어하기 안 함"이 "영영 버림"을 뜻하지는 않는다.

## 17. 백그라운드 수집은 foreground service로 상주시킨다

- 날짜: 2026-07-27
- 상태: 확정

수집기를 상시 알림을 띄운 foreground service로 상주시키고, 온보딩에서 배터리
최적화 예외를 요청한다. WorkManager 주기 실행에 의존하지 않는다.

이유: 실제 최대 적은 평균 정확도가 아니라 삼성/샤오미 등의 공격적 앱 종료와
Doze다. 여기서 데이터가 유실되면 그대로 "물어볼 게 없는 밤"이 된다. 개인용이라
상시 알림 하나는 감수할 만한 대가다.

트레이드오프: 상시 알림이 뜬다. 배터리 예외는 사용자가 직접 허용해야 하므로
온보딩에서 왜 필요한지 설명하는 단계가 필요하다. Geofence는 여전히 이벤트
기반으로 쓰되, 상주 서비스에서 주기적 위치 폴링으로 유실을 보정한다.

## 18. API 키는 APK의 BuildConfig에 주입한다

- 날짜: 2026-07-27
- 상태: 확정

`secrets.properties`의 키를 빌드 시 `BuildConfig`로 주입한다. 릴레이 서버를
두지 않는다. 이는 CLAUDE.md의 "하드코딩 금지"와 배치되지 않는다 — 그 규칙은
"소스에 적어 커밋하지 말라"이지 "기기에 두지 말라"가 아니다.

이유: 릴레이 서버는 "로컬 우선" 원칙과 충돌하고 운영 부담을 만든다. 단일
사용자·개인 기기에서 릴레이의 이득이 없다.

인정하는 위험: 키가 APK 안에 있어 디컴파일하면 추출된다. 개인 기기라 실질
위협은 낮다고 판단한다. 이 판단이 바뀌면(예: 앱을 남에게 준다) "최초 실행 시
직접 입력 → Keystore 저장"으로 옮긴다. 그 경로를 열어두기 위해 키 접근을
한 곳(설정/시크릿 프로바이더)으로 감싼다.

## 19. 세션 중에는 wake lock으로 화면을 켜 둔다

- 날짜: 2026-07-27
- 상태: 확정 (단, 아래 완화 조건과 함께)

대화 세션 동안 wake lock으로 화면을 계속 켜 둔다. 화면이 꺼지면 세션이 끊기는
문제를 가장 단순하게 없앤다. 화면이 켜져 있으므로 앱이 포그라운드에 남아
마이크·오디오가 유지되고, 세션 전용 foreground service가 따로 필요 없다.

**긴장과 완화:** 이 결정은 `concept.md`의 "취침 전은 무방비한 시간, 밤에
각성시키지 않는다 / 화면을 거의 보지 않는다"와 정면으로 부딪힌다. 밝은 화면은
각성을 부른다. 따라서 다음을 필수 조건으로 함께 둔다.

- 세션 화면은 **검은 배경 · 최소 밝기**로 강제한다(시스템 밝기와 무관하게).
- 시각 정보를 담지 않는다. 사실상 오디오 앱이라는 원칙은 유지된다 — 화면은
  "켜져 있을 뿐 볼 것이 없는" 상태다.
- 실사용에서 눈부심·배터리가 문제로 확인되면 결정 15/17에서 쓰는 foreground
  service 방식(화면 꺼진 채 지속)으로 옮길 수 있게, 화면 제어를 세션 로직에서
  분리해 둔다.

## 20. 밤 준비 트리거는 귀가(집 지오펜스 진입) 기반 적응형으로 한다

- 날짜: 2026-07-27
- 상태: 확정

고정 시각이 아니라 집 지오펜스 진입 후 일정 시간 뒤에 브리핑·첫 질문 생성·알림
을 트리거한다.

이유: 고정 시각은 그때 아직 밖(회사·이동 중)이면 브리핑이 반쪽이 된다.
귀가를 기준으로 삼으면 하루 데이터가 대체로 확정된 뒤에 준비가 돌아 "데이터가
준비됐다"는 보장에 강하다.

보완이 필요한 경계:
- 귀가 이벤트가 안 잡히거나 늦으면(결정 17의 유실 보정에도 불구하고) 준비가
  안 뜬다. **늦은 시각 안전망(예: 특정 시각까지 트리거가 없으면 강제 실행)**을
  둔다.
- 브리핑·첫 질문 생성은 Claude API 백그라운드 호출이다. 실패/오프라인 시
  질문 없이 "오늘 어땠어요?"로 시작하는 폴백을 준비한다.
- Health Connect 동기화 지연으로 트리거 시점에 오늘 수면 데이터가 아직 없을
  수 있다. 브리핑은 "있는 만큼"으로 만든다.

## 21. 기기 밖으로 나가는 데이터를 전수 목록으로 고정한다

## 22. 인물 이름은 프로필 목록으로 사후 교정한 뒤 일기에 넣는다

- 날짜: 2026-07-27
- 상태: 확정

diary-writer에 넘기기 전, transcript의 인물 이름을 프로필 인물 목록과 대조해
STT 오인식을 보정한다(유사 발음 → 등록된 이름으로 치환). **원본 transcript는
보정하지 않고 그대로 보존한다** — 교정은 일기 생성 입력에만 적용된다.

이유: `voice.md`가 걱정한 대로 실제 병목은 평균 정확도가 아니라 고유명사다.
오인식된 이름이 그대로 일기에 박히면 1년 뒤 사람 이름이 틀려 있다. 프로필에
이미 인물 목록이 있으므로(결정 8) 그것을 교정 사전으로 재사용한다. CLOVA
키워드 부스팅(가능하면)과 이 사후 교정은 같은 목록을 쓰는 이중 방어다.

주의: 목록에 없는 사람 이름은 못 고친다. 교정은 "등록된 인물"에 한한다.
원본이 보존되므로 틀렸어도 원문에서 되짚을 수 있다.

## 23. 문체 레퍼런스는 수정본 우선, 없으면 원본을 넣는다

- 날짜: 2026-07-27
- 상태: 확정

diary-writer에 넣는 최근 일기 레퍼런스는 사용자가 고친 수정본이 있으면 그것을,
없으면 원본 생성물을 쓴다.

이유: `scope.md`가 "일기 직접 수정 = 문체 학습의 유일한 경로"라 한 것을 실제로
닫는 결정이다. 수정본이 다음 생성의 few-shot이 되어야 초반의 어색함이 점점
사용자 문체로 수렴한다. 원본만 넣으면 어색함이 고정된다.

따라오는 구현: 일기에 **"수정됨" 상태와 수정본**을 DB/파일 양쪽에 두고, 레퍼런스
선택 시 수정본을 우선 조회한다. 원본도 버리지 않는다(원본 vs 수정본 비교가
나중에 문체 방향을 보는 자료가 된다).

## 24. "대화가 성립한 날" = 일기가 생성됐고 사용자가 지우지 않은 날

- 날짜: 2026-07-27
- 상태: 확정

`scope.md` 완료 기준("2주간 성립한 날 5일 이상")의 성립을 이렇게 정의한다:
**그날 일기 파일이 생성됐고, 사용자가 그것을 지우지 않았다.**

이유: 측정 가능해야 완료 기준이다. 턴 수 같은 기계적 임계값 대신 **삭제를
품질 신호로 삼는다** — 결정 13에 따라 미완 세션도 일기가 생성되지만, 부실한
일기는 사용자가 지우므로 자동으로 성립에서 빠진다. 사람의 판단을 별도 UI 없이
빌려오는 방식이다.

전제: 일기 뷰어에 삭제가 있어야 한다(어차피 필요). "안 지움"이 곧 "읽을 만했다"
의 최소 신호다.

## 25. 일일 상한 도달 시 이번 턴까지 마치고 담백하게 종료한다

- 날짜: 2026-07-27
- 상태: 확정

대화 도중 일일 토큰 상한에 닿으면, 진행 중인 턴은 끝까지 마친 뒤 "오늘은
여기까지"로 자연스럽게 종료한다. 문장 중간에 끊는 하드 스톱은 하지 않는다.

이유: 상한은 루프 버그 같은 사고를 막는 안전장치이지(결정 근거 `voice.md`)
대화를 죽이는 도구가 아니다. 밤에 문장이 중간에 끊기면 최악의 UX다.

경계: 종료 후에는 결정 13에 따라 그 시점까지의 대화로 일기가 생성된다. 하드
스톱은 상한을 크게 초과하는 폭주(루프 버그)에만 최후 수단으로 남긴다. 무료
폴백(Android TTS + 텍스트)으로 계속하는 방안은 v1에서 넣지 않는다 — 상한의
취지가 "오늘은 그만"이라 무료로 우회해 계속 쓰는 것은 목적에 어긋난다.

## 26. 형상 관리 — 짧은 브랜치+셀프리뷰, public, pre-commit 훅, 결정 번호 참조

- 날짜: 2026-07-27
- 상태: 확정 (전체는 `workflow.md`)

1인·AI 주도·개인 데이터 금지라는 세 제약에 맞춘 가벼운 전략.

- **브랜치:** 짧은 브랜치에서 작업 → `/code-review`로 AI 코드 확인 → `main`

  관문". GitFlow는 개인 앱에 과하다.
- **원격:** GitHub 공개. `INDEX.md`의 raw URL 워크플로우가 인증 없는 접근을
  전제로 하기 때문. 개인 데이터·키를 절대 커밋하지 않으므로 공개가 성립한다.
- **안전망:** `.gitignore` + `scripts/git-hooks/pre-commit`(민감 경로·`sk-ant-`

  걸며 로컬 설정이라 clone마다 재설치한다.
- **커밋:** 논리 단위 1커밋, 설계가 걸리면 메시지에 결정 번호 참조
  (`... (decisions #17)`). 히스토리가 `decisions.md`의 "왜"로 이어진다.

트레이드오프: 공개 저장소라 실수 한 번이 곧 유출이다. 그래서 안전망을 훅까지
3중으로 두는 것이 이 결정의 값어치다.

## 28. 수집은 FGS 상주가 아니라 "FGS 짧게 + AlarmManager 재기동"으로 (결정 17 개선)

- 날짜: 2026-07-28
- 상태: 확정 (결정 17을 플랫폼 제약에 맞춰 구체화)

결정 17은 "foreground service 상주"였다. 그런데 Android 14는 `dataSync` FGS를
하루 누적 6시간으로 제한해, 문자 그대로 24시간 상주가 불가능하다.

그래서 상주 대신: **수집 서비스는 시작되면 한 번 스냅샷하고, 다음 실행을
AlarmManager(inexact, Doze 허용)로 예약한 뒤 스스로 멈춘다.** FGS를 매 수집마다
짧게만 쓰므로 6시간 제한에 걸리지 않는다. 지오펜스는 이미 이벤트 기반이라
상주가 필요 없었다 — 상주로 지키려던 "수집이 안 죽음"은 배터리 최적화 예외 +
AlarmManager + 지오펜스 GMS 백엔드로 달성한다.

즉 결정 17의 목적(삼성에서 수집이 죽지 않게)은 유지하고, "상주"라는 수단만
플랫폼에 맞게 바꿨다. 스냅샷 주기가 실사용에서 부족하면 WorkManager 주기 실행으로
옮기는 것도 열려 있다.

## 29. 대화는 빠른 모델, 일기는 깊게 생각하는 모델로 나눈다 (결정 5 개선)

- 날짜: 2026-07-28
- 상태: 확정 (모델·파라미터 실물은 `ai/AnthropicClient.kt`)

결정 5는 "대화·일기 모두 Sonnet 5"였다. 실사용 감각상 둘의 요구가 다르다:
대화는 밤에 주고받으니 **속도**가, 일기는 하루치 수집·대화를 종합하니 **깊은
사고**가 중요하다.

- **대화: `claude-sonnet-5`, thinking 끔, effort `low`.** Sonnet 5는 thinking을
  생략하면 adaptive가 켜져 느려지므로 **명시적으로 끈다.** 따뜻한 인터뷰 품질은
  낮은 effort로도 충분하고, 턴 지연이 짧아진다.
- **일기: `claude-opus-4-8`, adaptive thinking, effort `high`.** 하루 1회라
  비용이 미미하고(결정 5의 "Opus는 과하다"를 일기에 한해 뒤집는다), 종합·성찰이
  필요한 작업이라 가장 똑똑한 모델 + 깊은 사고가 값어치를 한다. 사고가 토큰을
  먹으므로 max_tokens를 넉넉히(8192) 준다.

플랫폼 제약: 이 모델들에서 `budget_tokens`·`temperature`는 제거되어 보내면 400.
사고 깊이는 `thinking.type` + `output_config.effort`로만 제어한다. 잔작업용
Haiku(결정 5)는 아직 미사용.

## 30. STT/TTS를 v1에서 뺀다. 텍스트 기반으로 확정

## 31. 앱을 "매일 여는 홈"과 "한 번 만지는 설정"으로 나눈다

- 날짜: 2026-07-28
- 상태: 확정 (사용자가 4개 선택지 모두 확정)

그동안 화면 하나(구 `MainActivity`)에 권한 요청·소스별 읽기·지오펜스 등록·수집
서비스·이벤트 확인이 다 얹혀 있었다. 이건 개발용 테스트 하네스였고, 매일 밤 쓰기엔
투박했다. UX 관점에서 재구성:

- **홈(`MainActivity`)**: 날짜 헤더 + 큰 "오늘 밤 이야기하기" + 지난 일기 목록 +
  ⚙설정. 매일 여는 화면은 이 세 가지만.
- **설정 필요 카드**: 1회성 설정(건강·사진·위치·알림·배터리 예외·지오펜스) 중
  아직 안 된 것만 홈 상단 카드에 이름으로 보여준다. 다 되면 카드가 사라진다.
  판정은 `SetupStatus.missing()` 한 곳에서. 지오펜스 등록은 런타임 권한이 아니라
  SharedPreferences 플래그(`markGeofencesRegistered`)로 본다.
- **설정 화면(`SettingsActivity`)**: 구 테스트 하네스를 통째로 옮긴 뒷단. 권한·
  지오펜스·수집·개발용 읽기가 여기 모인다. 자동화되는 것들은 한 번 만지면 끝.
- **지난 일기(`DiaryViewerActivity`)**: 날짜 목록 → 가벼운 마크다운 렌더 → 수정.
  수정본은 다음 일기 생성 때 문체 레퍼런스로 곁들인다(결정 23 연결).
- **대화 화면**: 채팅 말풍선(내 말 오른쪽 primaryContainer, 상대 왼쪽
  surfaceVariant) + 새 턴마다 자동 스크롤 + 응답 대기 타이핑 버블.

원칙: 자동화되는 설정은 눈앞에서 치우고, 매일의 동선(대화 → 일기)만 홈에 남긴다.

## 32. 라이징 프로필 레이어 — 앱이 사용자를 알고, 계속 알아간다

- 날짜: 2026-07-28
- 상태: 확정

- **정적 프로필**: `personal/persona.md`(gitignore) → 빌드 시 앱 자산으로 복사
  (`copyPersona`, prompts와 같은 패턴). `PersonaLoader`가 읽어 인터뷰어 시스템

- **연속성**(`Continuity`): 오늘 센서(DayBriefing)와 별개로 지난 밤들에서 이어갈
  실마리 — 최근 일기 2편, 접어둔 `[heavy]` 주제(최근 2주 메시지 스캔), 학습분.
- **학습**(`PersonaMemory`): 일기 저장 후 그 대화에서 새로 드러난 '오래 갈 사실'을
  최대 3개 추출해 기기 내 `persona_learned.md`에 누적. 정적 프로필을 보완한다.
- 조립 순서: 인터뷰어 + 프로필 + 연속성 + 오늘 브리핑.

원칙: 프로필은 나열·규정용이 아니라 **질문의 각도와 밤의 온도**를 고르는 배경이다
(CLAUDE.md "라이프로깅은 질문 재료"와 같은 결). 민감 정보(성적 지향·재무)는
프로필에 원문 대신 다루는 태도만 적고, 재무는 사용자가 먼저 꺼낼 때만 받는다.
개인 자료는 저장소 밖(`personal/`, `C:\Personal\나의 분석자료`)에 두고 커밋 금지.

## 35. 일기 본문에 장면 사진을 넣는다 (Coil)

- 날짜: 2026-07-28
- 상태: 확정

diary-writer.md는 원래 장면 사진 삽입을 허용했지만 실제 URI 파이프라인이 없었다.
사용자 요청으로 Coil을 추가해 일기 속 사진을 렌더한다. "센서 데이터를 일기에
나열하지 마라"(CLAUDE.md)의 예외 — 사진은 센서 수치가 아니라 장면 콘텐츠이고,
diary-writer.md가 명시적으로 허용한다. 걸음·위치 숫자는 여전히 금지.

파이프라인:
- `MediaStorePhotoReader.readTodayPhotoRefs`: 오늘 사진의 content:// URI를 시간순
  최대 12장. 이미지 바이트는 앱이 들지 않고, 렌더 시 Coil이 권한으로 읽는다
  (v1 '메타데이터만' 기조는 유지 — URI는 참조지 내용이 아님).
- `DiaryPhotos.promptSection`: 작성기에 "오늘의 사진"을 번호+시각으로 제시.
- 작성기는 `![](사진N)` **번호 자리표시자**만 쓴다. LLM이 긴 content:// URI를
  그대로 뱉으면 자주 훼손하기 때문. `DiaryPhotos.resolve`가 실제 URI로 치환한다.
- `ui/MarkdownText`가 `![](uri)`를 Coil `AsyncImage`로 렌더(없으면 "(사진)").

비전(사진 내용 이해)은 여전히 v2. 지금은 시각을 단서로 배치하고, 억지로 끼워넣지
않게 프롬프트로 막는다. S23+에서 실제 content:// 사진 인라인 렌더 확인.

## 36. 대화 로그는 평문으로도 남긴다 (결정 15 부분 완화)

- 날짜: 2026-07-29
- 상태: 확정

결정 15에서 DB를 SQLCipher로 암호화했지만, 대화를 되짚어 인터뷰어 프롬프트를
개선하려면 사람이 로그를 바로 읽어야 한다(예: v1이 너무 소극적이라 v2로 고친 건
일기 결과물로 역추적했다 — 로그가 있었으면 즉시 봤다). 사용자가 "대화 로그는
암호화하지 말라"고 요청.

- 앱 동작용 저장(resume·이력)은 그대로 암호화 Room DB에 둔다. 마이그레이션
  위험을 피하고 센서·위치 데이터 보호는 유지.
- 이와 별개로 `TranscriptLog`가 세션당 평문 파일 `Transcripts/<날짜>.md`를 남긴다.
  헤더에 그 세션의 시스템 프롬프트(프로필·연속성·브리핑 포함)를 통째로 박아,
  "AI가 무엇을 보고 그렇게 답했는지"를 그대로 재구성할 수 있게 한다. 새 턴이
  생길 때만 append(resume 로드 시 중복 없음).
- 개인용·단일 사용자·본인 기기라 가능한 선택. 이 파일엔 프로필(빚·성적 지향 등)과
  대화 전체가 평문으로 들어가므로 **절대 커밋 금지**(.gitignore: Transcripts/).
  adb pull로 꺼내 분석한다.

## 37. 컨셉 전환: 밤 한 번 → 하루 종일 틈틈이, 저녁에 일기로 마무리

- 날짜: 2026-07-29
- 상태: 확정 (사용자 지시)

원래는 "잠들기 전 침대에서 한 번"이었다(결정 19의 밤 전제). 실제로 써보니 하루를
밤에 몰아 떠올리는 것보다, **하루 중 틈틈이(출근 직후·점심·이동 중·저녁) 그때그때
말하고, 저녁에 일기로 마무리**하는 게 "그때 무슨 생각이었나"를 더 잘 남긴다.

- **세션 모델**: 하루 = 한 대화 스레드(기존 sessionDate 그대로). 앱을 열 때마다
  오늘 대화에 이어붙고, '오늘 하루 마무리 · 일기 쓰기'로 그날을 닫는다.
- **라이브 컨텍스트**(`NowContext`): 매 메시지 직전에 지금의 시각·요일·시간대·위치
  (`LocationNow`가 마지막 위치를 집·회사와 비교)를 시스템 프롬프트에 덧붙인다.
  AI는 이걸로 "수요일 오전 9시 반, 회사 근처 → 방금 출근" 같은 판단을 한다.
  일정(캘린더)은 결정 38에서 붙인다.
- **프롬프트 v3**: "밤/잔다" 전제를 걷어내고 '지금을 읽어라' 지침 추가. 아침엔
  하루를 여는 톤, 낮엔 지금, 저녁·밤엔 되짚는 톤. 시각·위치를 그대로 읊지 말 것.
- **UI 문구**: "오늘 밤 이야기하기"→"지금 이야기하기", "이제 그만"→"오늘 하루
  마무리 · 일기 쓰기". 어두운 테마(결정 19)는 유지하되 '밤 전용' 전제는 폐기.

후속: 틈틈이 알림(앱이 상황 맞춰 먼저 말 걸기, 사용자 선택)과 캘린더 연동.

## 38. 캘린더 연동 — 오늘 일정을 질문 재료로

- 날짜: 2026-07-29
- 상태: 확정

삼성 캘린더를 포함해 기기에 동기화된 모든 캘린더는 안드로이드 표준
`CalendarContract`로 노출되므로 벤더 SDK 없이 `READ_CALENDAR` 권한만으로 읽는다.

'설정 필요' 카드에 '캘린더' 항목 추가.

## 39. 틈틈이 알림 — 앱이 먼저 말 걸기

- 날짜: 2026-07-29
- 상태: 확정 (사용자 선택: "틈틈이 알림으로 물어봐줘")

하루 종일 대화 컨셉(결정 37)을 살리려면, 사용자가 열기만 기다리지 말고 앱이
상황에 맞춰 먼저 슬쩍 말을 걸어야 한다.

- `NudgeScheduler`: 깨어 있는 몇 지점(10:00·13:00·16:30·21:00)에 AlarmManager로
  예약(inexact). 앱 시작·부팅·발화 후 재예약. 기본 켜짐, 설정 토글로 끔.
- `NudgeReceiver`/`Nudger`: 깨어나면 `ConversationContext`(화면과 동일)로 지금
  상황에 맞는 한마디를 생성한다. 그 한마디는 **알림 + 오늘 대화의 assistant 턴**
  으로 저장돼, 탭하고 들어오면 이어서 답할 수 있다.
- 안 거는 경우: 알림 꺼짐 / 오늘 일기를 이미 씀(하루 마무리) / 방금(90분 내)
  대화함. 답 없이 assistant 턴이 쌓일 수 있어 `normalize`로 연속 동일 역할을 합쳐
  API 교대 규칙을 지킨다.
- 공유화: 시스템 프롬프트 조립을 `ConversationContext`로 빼 화면과 알림이 같은
  프롬프트(인터뷰어+프로필+연속성+브리핑+지금)를 쓰게 했다.

## 40. 추천 답변 + 대화/추천 모델 Sonnet 5 보통

- 날짜: 2026-07-29
- 상태: 확정 (사용자 요청)

빈 입력창 앞의 막막함을 덜기 위해, 상대(인터뷰어)의 말 뒤 내 차례마다 문맥 기반
추천 답변 2~3개를 입력창 위 칩으로 띄운다. 클릭하면 입력창에 채워지고(바로 전송이
아니라 고쳐 보낼 수 있게), ↻ 아이콘으로 다른 추천을 다시 받는다.

- `Task.SUGGEST`(Sonnet 5, effort medium, thinking off, max_tokens 400) + `reply-suggester.md`.
- 추천은 서로 다른 방향(길게/짧게/회피)을 일부러 섞어, 고르는 것만으로 상태가 드러나게.
- 저장하지 않는다(대화 턴 아님). `turns` 마지막이 assistant일 때만 생성, 전송 시 초기화.
- 모델: 대화 답변·추천 둘 다 **Sonnet 5 보통(medium)**으로. 기존 대화는 effort low
  였고 medium으로 올림. 일기·회고는 그대로 Opus 4.8.
